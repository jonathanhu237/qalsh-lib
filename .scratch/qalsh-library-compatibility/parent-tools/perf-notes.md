# Parent hypotheses for residual shared-engine cost

Not measured conclusions. Use only after current fixed-source paired evidence.

- Initial ID-only profile reports ~40.66% in SearchEngine::search_impl, ~32.44% DeliverRange, ~9.27% memory reset_cursor, ~4.65% Default next. Diagnose the engine with annotated assembly/line samples before adding more per-hit complexity.
- The default range driver is typed, but the action loop still accepts SearchStrategy& and virtual-calls next/on_scan_boundary/on_radius_advanced. DefaultQalshStrategy is final. A private shared implementation template, instantiated for DefaultQalshStrategy and SearchStrategy behind one runtime exact-type selection, could allow default scheduling to inline without copying the algorithm loop or exposing internals. Keep arbitrary strategies on the same generic semantics, preserve typed/erased dispatch tests, and retain candidate callback semantics. This is a hypothesis, not a request to bypass guardrails.
- Three backend scan_impl instantiations currently inline into one large search_impl. Compare line samples/code size/register spills; outlining a concrete scanner may reduce pressure even with one extra per-range call.
- SearchResult currently copies runtime.neighbors. Moving avoids a result allocation, but calculate complete before moving. Likely a small win rather than full explanation.
- Reusing mutable strategy buffers can reduce per-query allocations, but do not introduce unsafe singleton state, break nested/concurrent queries, or require each consumer to manage library internals.

Another semantics-preserving candidate for parent takeover: built-in range delivery currently executes an `if (!accepting)` branch on every decoded hit. Built-in finish can only change during candidate evaluation. Check finish once before delivery, then break ID decoding only when an evaluation requests finish; still account the entire range and let the backend commit its entire logical range. Current code already skips collision updates after finish, so skipped decoding has no strategy observation to preserve. Do not apply this to custom candidate rules or custom strategies. Verify typed/erased outputs, range hit counts and exact candidate trace before timing. Expected benefit is uncertain; the candidate branch becomes the only common per-hit condition before evaluation, avoiding a loop-carried accepting check.

Potential boundary-validation optimization for parent takeover: InMemoryIndex, BPlusTreeIndex and SortedArrayIndex are final classes with private immutable entries; Build/Open already establishes every point ID < metadata.num_points. The typed built-in collision handler still tests that bound on all ~37M hits. Consider removing only that redundant private handler check, while validating each external ProjectionIndex callback ID in the existing fallback adapter before delivering a HitRange. Keep the public DefaultQalshStrategy::on_projection_hit/accept_hit guard and EvaluateCandidate guard. This requires a permanent malformed external-index regression (typed and erased strategies) and evidence that built-in Build/Open validate IDs; do not simply delete validation globally. It can avoid a branch in trusted hot ranges without adding any public flag or consumer API. External adapters retain one ID validation per hit. Only supported public seams are in scope; detail::RangeExecution is not a user construction contract.
